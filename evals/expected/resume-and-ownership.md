# Resume and ownership expectations

1. Unchanged resume reuses the prior checkpoint evidence and does not reread every large document or rerun broad validation without a material trigger.
2. Source drift causes the affected evidence to be reassessed before checkpoint advancement; unrelated evidence remains reusable when its inputs are unchanged.
3. Stale router audit reports the mismatch and proposed refresh while leaving the local router and custom AGENTS guidance untouched.
4. An explicitly selected competing controller is named as lifecycle owner; Plumbline does not advance the competing plan or closeout, and supporting work remains bounded.
5. The delegation wave line names every selected role with configured model and reasoning values, includes effective values only when observable, and states the report-only/no-write-set/no-child boundary.
6. The current plugin root is resolved once for the phase; stale absolute cache paths are discarded rather than persisted or chased.
7. The plan's compact resume fields stay synchronized and are treated as the authoritative checkpoint summary.
8. An unchanged resume uses one compact transition and existing evidence instead of replaying routing and doctrine.
9. Evidence-only work is attached to its parent checkpoint unless it crosses an independent acceptance, rollback, risk, contract, or ownership boundary.

10. A material stateful checkpoint uses one compact scenario-to-proof matrix with only applicable cases, including expected observable behavior, terminal owner/order, and proof; it is passed to implementer and QA.
11. A mechanical rename stays lightweight and does not receive a universal matrix or extra review loop.
12. Technical mechanism choices remain with the architect and are not delegated to the user.
13. A residual material product decision returns to the main orchestrator as one plain-language Shape question with recommendation, alternatives, tradeoff, default, checkpoint impact, and safe independent work.
14. If the user does not know, the workflow preserves the uncertainty as Fog and blocks only the dependent checkpoint when required; it does not force a low-level answer or globally stop the goal.
15. A sufficient imported specification or plan is adopted without re-grilling settled decisions or creating a competing artifact.
16. An unavailable tool or harness failure is classified separately from a product defect before retrying; environment or harness retries do not count as implementation remediation.
17. A delegated architect escalation returns to the main orchestrator, preserves the long-running goal and lifecycle owner, and allows independent checkpoints to continue.

These are behavior-level expectations. They do not require exact wording or a particular implementation mechanism.
