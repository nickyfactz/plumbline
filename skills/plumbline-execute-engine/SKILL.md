# Execute engine

At task start or resume, read the controlling plan's compact resume record, external work order, or supplied execution artifact first. Treat checkout/worktree identity, HEAD/last_verified_commit when present, the artifact/plan-record hash, and relevant local agent hashes as the resume fingerprint. If that fingerprint is unchanged, read the compact record, Git delta, and next action only. A new session, compaction, or conversational resume alone does not invalidate evidence. Inspect the current checkpoint or supplied execution boundary, its referenced contract sections, validation commands, and last_verified_commit when present; read larger source/spec sections only when a reference or material trigger requires them. Resolve the current Plumbline installation root once at phase entry and use it for all references paths. Keep one active execution boundary for this task. By default, Execute traverses every remaining checkpoint in serial/dependency order; a checkpoint boundary is an internal handoff, not a user-prompt stop. Do not advance a blocked or reopened checkpoint, but continue other safe checkpoints when the topology permits.

At each checkpoint, inspect the current checkout and the delta from the last verified state first. Read the exact checkpoint and its referenced contract sections, changed files, and relevant canonical documentation. Reuse prior completion evidence when the fingerprint and referenced inputs are unchanged; do not reread whole documents or rerun broad validation merely because a new checkpoint began. Reassess prior evidence only after a fingerprint change, relevant source/spec/plan/config/agent change, failed or newly relevant check, contract-boundary change, defect, or stale-evidence concern.

Before implementation, perform a conditional artifact sufficiency preflight. Accept a user-supplied or repository-local plan, work order, or specification with execution topology and proof even when it is not Plumbline-generated. If a sufficient specification has no separate plan, recommend a companion plan but do not block execution when the artifact already defines the next safe slice and acceptance. If no artifact is executable and the missing plan or product decision is material, recommend Plan or Shape; do not fail merely because the repository lacks Plumbline paths or frontmatter. Report only adoption, a companion recommendation, competing candidates, or a real blocker.

## Full-plan traversal and execution judgment

Normal Execute means full-plan mode. After a checkpoint's bounded work, review, focused proof, and main-thread integration are complete, update the plan's resume record, select the next safe checkpoint, and continue without waiting for a user prompt. Do not return `Ready for Acceptance` between checkpoints. Use checkpoint-by-checkpoint mode only when the user explicitly asks to run one checkpoint, pause after a named checkpoint, or require approval at each boundary. Do not require `/goal` or another long-horizon controller to traverse a multi-checkpoint plan.

Checkpoint closeout means that the worker reports back, the main thread integrates evidence, and the plan advances. It is not the final `$plumbline-closeout` operation, which remains the acceptance-led boundary for transient cleanup, integration, and publishing preparation.

Once an approved specification and plan are active, treat them as delegated product authority for execution. An architect or worker's `Shape question` label is an internal escalation, not an instruction to invoke Shape or stop for the user. The main orchestrator resolves in-scope ambiguity from the approved outcome, repository evidence, prior decisions, and the safest reversible default; record the decision, assumption, or residual risk in the plan/spec. Reopen Shape or stop only for an explicit user gate, a destructive or irreversible action outside the approved authority, or a contradiction that has no safe in-scope default. If no safe default exists, block only the affected checkpoint and continue independent checkpoints; never terminate the active goal merely because a child raised the question.

Before advancing or saving plan state, verify exactly one current checkpoint, matching frontmatter status, and a next_safe_action for that checkpoint. Treat unresolved items as Acceptance blocker, Residual risk, Operational follow-up, or Future enhancement; only an Acceptance blocker stops advancement. Record rolling telemetry as timestamped sample evidence with its date or generation/window and keep stable acceptance assertions separate from changing counts.

On an unchanged resume or adjacent checkpoint, rely on the resume record and plan evidence. Use a compact state/transition line only when the phase, owner, evidence, or next action changed. Do not repeat the full route, doctrine, lifecycle declaration, or checkpoint narration.

Use the host's managed worktree for scoped/designed feature work when the host provides one. Never create, remove, register, or clean up worktrees from Plumbline instructions. Direct work and small fixes may stay on the active checkout. Inspect repository-owned environment setup before proposing changes; use absolute tools and environment variables, and treat borrowed resources as read-only.

The main thread is the only Git writer. Subagents receive bounded briefs with disjoint write sets, a named contract, expected evidence, and a no-Git/no-active-plan-edit rule. Serialize any shared-file or shared-contract work. Pause if a worker expands its write set.

Keep the dispatch invariant short: use only project-local roles, give report-only roles no write set, give an implementer only a bounded write set, keep Git in the main thread, and allow no worker children. Load references/subagent-orchestration.md immediately before the first actual delegation wave, not for direct work. Before that wave, inspect `.codex/agents/` and `.codex/config.toml` for Codex, or `.claude/agents/` for Claude Code; reuse the result while the checkout/worktree and those file hashes are unchanged. Recheck after a fingerprint change or explicit request. At each delegation wave, emit one compact line such as `Delegated wave: researcher [model=<host-native-model>, reasoning=<effort>] - Boundary: report-only; no write set; no child agents`, listing every selected role with its configured host-native model and reasoning/effort value. The report names the configured model slug and reasoning effort for Codex, or the host-native model and effort for Claude. Include effective model, reasoning/effort, or effective sandbox/permission values only when the host exposes a meaningful difference or the user asks; do not invent values or repeat unchanged configuration on resume. Inspect Git status/diff after the worker returns and never silently integrate unexpected edits. Use `Direct: <reason>` when an expected delegation cannot occur or hard read-only isolation is required but unavailable. Never select personal/global custom agents or any global fallback. Workers never spawn children; Codex `agents.max_depth = 1` is the project recommendation and Claude omits the `Agent` tool to express the same boundary.

At each checkpoint: read the exact referenced contract sections, implement the bounded vertical slice, run the narrowest meaningful checks, apply the runtime-value test gate from references/runtime-value-testing.md, integrate worker changes, and record material evidence and deviations in the controlling artifact. When a material-risk checkpoint has a compact scenario-to-proof matrix, pass that same matrix to the implementer and QA; do not invent extra scenarios or a second acceptance system. After a focused proof establishes a stable delta, obtain report-only QA before expensive broad, package, or live-stack gates when practical. Keep this ordering conditional: small, mechanical, or documentation-only work stays on the lightweight path. Choose the smallest complete implementation: minimize speculative code, dependencies, and abstractions, but do not omit required behavior, companion surfaces, failure/recovery paths, compatibility, or meaningful proof to make the diff smaller. Do not create a commit solely for a minor evidence note; batch related UAT or presentation corrections into one coherent review-pass commit unless they have an independent acceptance, rollback, risk, contract, or ownership boundary. Commit after focused validation when the user/repository requires it, the work must survive multi-session recovery, or the checkpoint creates a material contract or authorization boundary; otherwise batch adjacent evidence-only work until a coherent boundary. Before creating slice-specific evidence machinery, inspect the latest accepted equivalent and reuse its generic build, source-binding, receipt, install, or record path; add only behavior assertions that are genuinely slice-specific. A test is valuable when it protects stable public behavior or a plausible regression; a non-test check, manual UAT, static validation, or justified no-test outcome is allowed. Do not add tests that freeze prose, private structure, or literal configuration defaults.

Classify validation results before stopping or rerunning: product defect, contract gap, environment failure, test-harness failure, known unrelated baseline failure, or unavailable evidence. Record the classification and next action once. A new regression or checkpoint-invalidating product or contract failure stops the affected checkpoint; a known unrelated baseline failure may be recorded and bypassed when it does not affect the plan. Environment and harness failures are not model remediation and should not trigger repeated implementation retries; an inconclusive result or missing capability must be escalated. Do not stop for an ordinary in-scope product ambiguity after plan approval; resolve it with the execution judgment above. Stop only for an explicit user gate, destructive uncertainty, or a contradiction with no safe reversible path, preserving the active plan and continuing independent work where possible.

Record one lifecycle owner in the active plan. Report Lifecycle owner: Plumbline Execute only when ownership changes, a competing controller is selected, or the record is stale. Installed or enabled skills alone do not establish ownership. If another explicitly selected orchestration loop owns checkpoint selection, plan advancement, review sequencing, or closeout, do not stack a second lifecycle controller; use Plumbline only for the selected phase contract. Construction-policy skills may constrain implementation choices, but they do not become lifecycle controllers, add checkpoints, or weaken Plumbline's acceptance and ownership rules. Do not dispatch independent review while an implementer is still changing the reviewed write set; integrate first, then review the stable delta.

For a high-risk checkpoint involving material state, persistence, concurrency, security, a public contract, or cross-boundary ownership transfer, dispatch report-only QA on the first stable implementer delta before making material semantic repairs on the main thread and, when practical, before expensive broad/package/live gates. The main thread may inspect status/diff and fix a trivial integration issue, but substantial corrections return to the bounded implementer or reopen the checkpoint. A newly discovered contract or ownership invariant is a planning/architect trigger, not permission to expand the write set silently. The QA result belongs to the affected checkpoint; it does not end or globally block an active goal.

Every process artifact, announcement, or receipt must support recovery, validation, authorization, or ownership. Omit it when it serves none of those purposes.

Execute owns implementation, focused/full proof, acceptance-required canonical documentation, serial traversal of all remaining checkpoints, and the final stable-delta review needed to reach Ready for Acceptance after the complete plan is done. Closeout begins only after acceptance and owns final integration, transient cleanup, plan retirement, worktree/branch handling, and publishing preparation; Execute does not delete transient artifacts or publish.
