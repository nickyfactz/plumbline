# Execute engine

At task start or resume, read the controlling plan's compact resume record, external work order, or supplied execution artifact first. Treat checkout/worktree identity, HEAD/last_verified_commit when present, the artifact/plan-record hash, and relevant local agent hashes as the resume fingerprint. If that fingerprint is unchanged, read the compact record, Git delta, and next action only. A new session, compaction, or conversational resume alone does not invalidate evidence. Inspect the current checkpoint or supplied execution boundary, its referenced contract sections, validation commands, and last_verified_commit when present; read larger source/spec sections only when a reference or material trigger requires them. Resolve the current Plumbline installation root once at phase entry and use it for all references paths. Keep one active execution boundary for this task and never advance while it is Blocked or Reopened.

At each checkpoint, inspect the current checkout and the delta from the last verified state first. Read the exact checkpoint and its referenced contract sections, changed files, and relevant canonical documentation. Reuse prior completion evidence when the fingerprint and referenced inputs are unchanged; do not reread whole documents or rerun broad validation merely because a new checkpoint began. Reassess prior evidence only after a fingerprint change, relevant source/spec/plan/config/agent change, failed or newly relevant check, contract-boundary change, defect, or stale-evidence concern.

Before implementation, perform a conditional artifact sufficiency preflight. Accept a user-supplied or repository-local plan, work order, or specification with execution topology and proof even when it is not Plumbline-generated. If a sufficient specification has no separate plan, recommend a companion plan but do not block execution when the artifact already defines the next safe slice and acceptance. If no artifact is executable and the missing plan or product decision is material, recommend Plan or Shape; do not fail merely because the repository lacks Plumbline paths or frontmatter. Report only adoption, a companion recommendation, competing candidates, or a real blocker.

Before advancing or saving plan state, verify exactly one current checkpoint, matching frontmatter status, and a next_safe_action for that checkpoint. Treat unresolved items as Acceptance blocker, Residual risk, Operational follow-up, or Future enhancement; only an Acceptance blocker stops advancement. Record rolling telemetry as timestamped sample evidence with its date or generation/window and keep stable acceptance assertions separate from changing counts.

On an unchanged resume or adjacent checkpoint, rely on the resume record and plan evidence. Use a compact state/transition line only when the phase, owner, evidence, or next action changed. Do not repeat the full route, doctrine, lifecycle declaration, or checkpoint narration.

Use Codex-managed worktrees for scoped/designed feature work when the host provides them. Never create, remove, register, or clean up worktrees from Plumbline instructions. Direct work and small fixes may stay on the active checkout. Inspect repository-owned environment setup before proposing changes; use absolute tools and environment variables, and treat borrowed resources as read-only.

The main thread is the only Git writer. Subagents receive bounded briefs with disjoint write sets, a named contract, expected evidence, and a no-Git/no-active-plan-edit rule. Serialize any shared-file or shared-contract work. Pause if a worker expands its write set.

Keep the dispatch invariant short: use only project-local roles, give report-only roles no write set, give an implementer only a bounded write set, keep Git in the main thread, and allow no worker children. Load references/subagent-orchestration.md immediately before the first actual delegation wave, not for direct work. Before that wave, inspect .codex/agents/ and .codex/config.toml; reuse the result while the checkout/worktree and those file hashes are unchanged. Recheck after a fingerprint change or explicit request. At each delegation wave, emit one compact line such as Delegated wave: researcher [model=<slug>, reasoning=<effort>] - Boundary: report-only; no write set; no child agents, listing every selected role with its configured model slug and reasoning effort. Include effective model, reasoning, or effective sandbox values only when the host exposes a meaningful difference or the user asks; do not invent values or repeat unchanged configuration on resume. Inspect Git status/diff after the worker returns and never silently integrate unexpected edits. Use Direct: <reason> when an expected delegation cannot occur or hard read-only isolation is required but unavailable. Never select personal/global custom agents or any global fallback. Workers never spawn children; agents.max_depth = 1 is the project recommendation.

At each checkpoint: read the exact referenced contract sections, implement the bounded vertical slice, run the narrowest meaningful checks, apply the runtime-value test gate from references/runtime-value-testing.md, integrate worker changes, and record material evidence and deviations in the controlling artifact. Choose the smallest complete implementation: minimize speculative code, dependencies, and abstractions, but do not omit required behavior, companion surfaces, failure/recovery paths, compatibility, or meaningful proof to make the diff smaller. Do not create a commit solely for a minor evidence note; batch related UAT or presentation corrections into one coherent review-pass commit unless they have an independent acceptance, rollback, risk, contract, or ownership boundary. Commit after focused validation when the user/repository requires it, the work must survive multi-session recovery, or the checkpoint creates a material contract or authorization boundary; otherwise batch adjacent evidence-only work until a coherent boundary. Before creating slice-specific evidence machinery, inspect the latest accepted equivalent and reuse its generic build, source-binding, receipt, install, or record path; add only behavior assertions that are genuinely slice-specific. A test is valuable when it protects stable public behavior or a plausible regression; a non-test check, manual UAT, static validation, or justified no-test outcome is allowed. Do not add tests that freeze prose, private structure, or literal configuration defaults.

Classify validation results before stopping: a new regression or checkpoint-invalidating baseline failure stops execution; a known unrelated baseline failure may be recorded and bypassed when it does not affect the checkpoint; an inconclusive result or missing environment capability must be escalated. Stop for product decisions or destructive uncertainty and preserve the current checkpoint state.

Record one lifecycle owner in the active plan. Report Lifecycle owner: Plumbline Execute only when ownership changes, a competing controller is selected, or the record is stale. Installed or enabled skills alone do not establish ownership. If another explicitly selected orchestration loop owns checkpoint selection, plan advancement, review sequencing, or closeout, do not stack a second lifecycle controller; use Plumbline only for the selected phase contract. Construction-policy skills may constrain implementation choices, but they do not become lifecycle controllers, add checkpoints, or weaken Plumbline's acceptance and ownership rules. Do not dispatch independent review while an implementer is still changing the reviewed write set; integrate first, then review the stable delta.

For a high-risk checkpoint involving material state, persistence, concurrency, security, a public contract, or cross-language ownership transfer, dispatch report-only QA on the first stable implementer delta before making material semantic repairs on the main thread. The main thread may inspect status/diff and fix a trivial integration issue, but substantial corrections return to the bounded implementer or reopen the checkpoint. A newly discovered contract or ownership invariant is a planning/architect trigger, not permission to expand the write set silently.

Every process artifact, announcement, or receipt must support recovery, validation, authorization, or ownership. Omit it when it serves none of those purposes.

Execute owns implementation, focused/full proof, acceptance-required canonical documentation, and the final stable-delta review needed to reach Ready for Acceptance. Closeout begins only after acceptance and owns integration, transient cleanup, plan retirement, worktree/branch handling, and publishing preparation; Execute does not delete transient artifacts or publish.
