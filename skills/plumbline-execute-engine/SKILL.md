# Execute engine

At task start or resume, read the active plan's compact resume record or controlling work order first. Then inspect only the current checkpoint, its referenced contract sections, Git status/delta, validation commands, and `last_verified_commit`. Read canonical docs or larger source/spec sections only when the checkpoint references them or a material trigger makes prior evidence stale. Resolve the current Plumbline installation root once at phase entry and use it for all `references/...` paths. Keep one active checkpoint and never advance while it is `Blocked` or `Reopened`.

At each checkpoint, inspect the current checkout and the delta from the last verified state first. Read the exact checkpoint and its referenced contract sections, changed files, and relevant canonical documentation. Reuse prior completion evidence when those inputs are unchanged; do not reread whole migration documents or rerun broad validation merely because a new checkpoint began. Reassess prior evidence only after a new task or resume, checkout/worktree change, relevant source/spec/plan/config/agent change, failed or newly relevant check, contract-boundary change, defect, or stale-evidence concern.

On an unchanged resume or adjacent checkpoint, emit one compact state/transition line and rely on the resume record and plan evidence. Do not repeat the full route, doctrine, lifecycle declaration, or checkpoint narration unless the phase, owner, evidence, or next action changed.

Use Codex-managed worktrees for scoped/designed feature work when the host provides them. Never create, remove, register, or clean up worktrees from Plumbline instructions. Direct work and small fixes may stay on the active checkout. Inspect repository-owned environment setup before proposing changes; use absolute tools and environment variables, and treat borrowed resources as read-only.

The main thread is the only Git writer. Subagents receive bounded briefs with disjoint write sets, a named contract, expected evidence, and a no-Git/no-active-plan-edit rule. Serialize any shared-file or shared-contract work. Pause if a worker expands its write set.

Before the first delegation wave in an execution session, inspect the project-local `.codex/agents/` and `.codex/config.toml`. Reuse that verification for later waves while the checkout/worktree and those file hashes are unchanged. Recheck after a new task or resume, a checkout/worktree change, a relevant config or agent change, or an explicit request. Select the matching local `researcher`, architect, `implementer`, or `qa-auditor` only when the brief is bounded and the local configuration is valid. Report-only roles (researcher, architect, and QA) get no write set; reject briefs that ask them to edit source, tests, scripts, documentation, or Git state. Their `sandbox_mode = "read-only"` is intent, not proof; a writable parent is normal for a goal and may affect the child's effective sandbox. At each delegation wave, emit one compact line such as `Delegated wave: researcher [model=<slug>, reasoning=<effort>] — Boundary: report-only; no write set; no child agents`, listing every selected role with its configured model slug and reasoning effort. Include effective model, reasoning, or sandbox values only when the host exposes a meaningful difference or the user asks; do not invent values or repeat unchanged configuration on resume. Inspect Git status/diff after the worker returns and never silently integrate unexpected edits. Use `Direct: delegation prohibited or effective read-only isolation unavailable` only when hard read-only isolation is required. Never select personal/global custom agents or any global fallback. Workers never spawn children; `agents.max_depth = 1` is the project recommendation.

At each checkpoint: read the exact referenced contract sections, implement the smallest vertical slice, run the narrowest meaningful checks, apply the runtime-value test gate from `references/runtime-value-testing.md`, integrate worker changes, record evidence and deviations in the plan, and commit only after focused validation passes and the checkpoint is a coherent recovery boundary or repository policy requires it. Batch evidence-only follow-up work when it has no independent acceptance, rollback, risk, contract, or ownership boundary. A test is valuable when it protects stable public behavior or a plausible regression; a non-test check, manual UAT, static validation, or justified no-test outcome is allowed. Do not add tests that freeze prose, private structure, or literal configuration defaults.

Classify validation results before stopping: a new regression or checkpoint-invalidating baseline failure stops execution; a known unrelated baseline failure may be recorded and bypassed when it does not affect the checkpoint; an inconclusive result or missing environment capability must be escalated. Stop for product decisions or destructive uncertainty and preserve the current checkpoint state.

At phase entry or resume, identify one lifecycle owner and emit `Lifecycle owner: Plumbline Execute` unless another controller was explicitly selected. Record it in the active plan and repeat it only when ownership changes or the record is stale. Installed or enabled skills alone do not establish ownership. If another explicitly selected orchestration loop owns checkpoint selection, plan advancement, review sequencing, or closeout, do not stack a second lifecycle controller; use Plumbline only for the selected phase contract. When Plumbline owns the lifecycle, invoke one matching engine and keep supporting skills bounded to their assigned work. Do not dispatch independent review while an implementer is still changing the reviewed write set; integrate first, then review the stable delta.
